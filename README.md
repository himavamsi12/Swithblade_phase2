# Swithblade

E-commerce storefront built with Next.js 16 (App Router), React 19, TypeScript and
Tailwind CSS 4, with a Medusa-style commerce admin on Payload 3 (Postgres/Supabase)
at `/admin`.

## Getting started

```bash
nvm use            # Node 24 (see .nvmrc)
pnpm install
cp .env.example .env.local   # fill in DATABASE_URL etc.
pnpm migrate       # create/upgrade the database schema
pnpm dev           # http://localhost:3000, admin at /admin
```

## Scripts

| Script                         | What it does                                    |
| ------------------------------ | ----------------------------------------------- |
| `pnpm dev` / `build` / `start` | Next.js dev server / production build / serve   |
| `pnpm check`                   | typecheck + lint + format check + tests (as CI) |
| `pnpm typecheck`               | Generates Next route types, then `tsc --noEmit` |
| `pnpm lint` / `lint:fix`       | ESLint (`eslint-config-next`, TypeScript rules) |
| `pnpm format` / `format:check` | Prettier (with Tailwind class sorting)          |
| `pnpm test` / `test:watch`     | Vitest + Testing Library                        |
| `pnpm migrate`                 | Apply Payload migrations, then `db:harden`      |
| `pnpm migrate:create <name>`   | Generate a migration after changing collections |
| `pnpm db:harden`               | RLS on all Payload tables, revoke API roles     |
| `pnpm generate:types`          | Regenerate `src/payload-types.ts`               |
| `pnpm generate:importmap`      | Regenerate the admin component import map       |

A pre-commit hook (Husky + lint-staged) lints and formats staged files. CI
(`.github/workflows/ci.yml`) runs typecheck, lint, format, tests and build.

## Structure

```
src/
  app/                 Routes only: layouts, pages, metadata, route handlers
    (frontend)/        Storefront root layout
      (storefront)/    Header/footer shell + shop pages
    (payload)/         Payload admin (/admin) and API (/api) root layout
  payload.config.ts    Payload config (collections, plugins, database)
  payload/             CMS schema: collections, plugin overrides, access,
                       admin UI (Medusa-style theme + dashboard), migrations
  components/
    ui/                Generic primitives (Button, ...), no business logic
    layout/            Site header/footer
  features/<domain>/   Everything for one business domain
    catalog/           types, repository (data access), components
  config/              Static site configuration
  lib/                 Framework-agnostic helpers (env, utils, format)
```

Rules of thumb:

- `app/` stays thin. Domain logic lives in `features/`.
- Data access goes through a feature's `repository.ts` (marked `server-only`).
  The catalog currently serves mock data; replace the repository, not the pages.
- Money is integer minor units (cents). Format with `formatPrice`.
- Env vars are validated in `src/lib/env.ts`. Add new ones to `.env.example`.

## Next.js 16 notes

- `middleware` is now `proxy` (`src/proxy.ts`). Not used yet.
- `params` / `searchParams` are Promises; use the global `PageProps<"/route">`
  and `LayoutProps<"/route">` helpers (generated by `next typegen`).
- `error.tsx` receives `retry`, not `reset`.
- **No root `loading.tsx`.** It makes Next stream a 200 before `notFound()`
  runs, so unknown product URLs become soft-404s (bad for SEO). Use local
  `<Suspense>` boundaries around slow data instead.

## Commerce admin (Payload)

Modelled on Medusa's modules and sidebar: Orders (returns, carts, payments),
Products (categories, collections, options, variants), Inventory, Customers
(groups, addresses), Promotions (campaigns), Price Lists, and Settings (users,
regions, tax regions, return reasons, sales channels, product types/tags,
locations & shipping, store). Built on `@payloadcms/plugin-ecommerce`.

- Staff sign in through `users`; shoppers through `customers`. The first staff
  account created becomes an admin.
- Stripe is enabled only when its keys are set.

### Customers (Supabase Auth → Payload)

Shoppers sign in with Supabase Auth (`/account`). A database trigger on
`auth.users` (migration `sync_supabase_customers`) mirrors every account into
Payload's Customers: sign-up creates it (email and Google), sign-in and email
confirmation update it, deleting the Supabase user unlinks it but keeps the
record. An existing customer with the same email is linked, not duplicated.
Customers is staff-only in Payload; shoppers never get a Payload session.

### Database rules (Supabase Postgres best practices)

- Tables live in the `payload` schema, not `public`, so Supabase's Data API
  can't reach them. Don't add `payload` to the Data API's exposed schemas.
- `pnpm db:harden` (run by `pnpm migrate`) enables RLS on every table and
  revokes `anon`/`authenticated`. Payload connects as the owner, unaffected.
- No schema auto-push, even in dev: change a collection, then
  `pnpm migrate:create <name>`, review the SQL, `pnpm migrate`.
- Runtime uses the transaction pooler (6543; Payload sends unnamed statements,
  so no prepared-statement issues); migrations use `DATABASE_MIGRATION_URL`
  (session pooler, 5432).
- TLS: `DATABASE_CA_CERT` is required in production so the certificate is
  verified. Pool size: `DATABASE_POOL_MAX` (1 on Vercel by default).
- Foreign keys and filter/sort columns are indexed; money is stored as exact
  `numeric` in minor units.
